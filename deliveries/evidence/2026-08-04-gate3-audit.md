## 1a. Blind Re-Derivation (Pre-Diff Expectations vs. Delivered Document Set)

### Written Pre-Derivation Expectation
Based strictly on the three-sentence design summary:
> *Players throw 3D dice in a contained arena and spend earnings forging individual faces under a zero-sum mass budget — mass moves between faces, never accumulates. Heavier faces pay superlinearly but land less often, so every forge is a trade-off. The server decides every roll outcome by weighted sampling; the client's 3D tumble is animation resolving to an already-decided face.*

A correct, production-grade document set for this system must contain:
1. **Threat Model (`THREAT_MODEL.md`):** Must define all critical assets (Cash, Mass budgets, Gems, Robux receipts, Gamepasses, Leaderboards, Vaults) and trust boundaries (Client->Server remotes, untrusted client runtime, persistence, MarketplaceService). It must explicitly defend against client outcome spoofing, physics manipulation, forge mass budget inflation, floating-point `NaN` validator exploits, receipt replay attacks, and clock tampering for offline vault claims.
2. **SRS (`SRS.md`):** Must detail testable functional requirements for arena presentation, server roll resolution, zero-sum forge operations (with non-trivial scaling costs), mass-coupled element payoffs, compounding streak math `(1+b)^s`, shape trade-offs (D4..D20), auto-roll server rates, offline vault math, ascensions/prestige, quests/spin/like goals, global log-scaled leaderboards, monetization receipts (with once-only starter bundle enforcement), responsive Scale-based UI, and fail-closed ProfileStore persistence. Every requirement must be testable without physical trajectory dependencies.
3. **HLD (`HLD.md`):** Must explicitly state the server authority model (server samples outcomes, client physics is visual animation only, server holds zero rigid-body state). It must map system topology, module breakdown (`ServerScriptService`, `ReplicatedStorage.Shared`, `StarterPlayerScripts.Client`), roll/forge/animation sequences, dependency review note for ProfileStore, and session-locking rules.
4. **API & Data Contract (`API_DATA_CONTRACT.md`):** Must enumerate all 16 inbound RemoteFunctions and 6 outbound RemoteEvents with exact signatures, types, zero-payload rules for rolls, validation ordering (finiteness `n==n` before sum checks), rate limit token buckets, complete DataStore schema template with explicit defaults for every field, bounded 200-entry `PurchaseIds` array, and log-scaled integer conversion for `OrderedDataStore`.
5. **Test Plan (`TEST_PLAN.md`):** Must specify an automated harness (`RunAll.server.luau`, `Fakes.luau`), 4 concrete execution procedures (P-1 static analysis, P-2 unit suite, P-3 static prohibition grep for `InvokeClient`/`ProcessReceipt`/`SetAsync`/`MessagingService`, P-4 11-step runtime smoke test), unit test suites UT-1..UT-11, integration suites IT-1..IT-5, and explicit coverage gaps.
6. **DevOps Record (`DEVOPS_RECORD.md`):** Must state 10 explicit operational decisions (single place with Studio sync, topic branches, Studio verification, secret locations/env vars, manual publish, analytics monitoring, zero-loss transaction tolerance, profile quarantine backups) and a dependency register for ProfileStore (MIT license, pinned release, actively supported).

### Expectation vs. Reality Comparison
- **Gaps Identified:** None. The document set strictly mirrors the blind re-derivation expectation. All six documents exist in `docs/blueprint/`, open with valid `CONSUMED-BY` headers, contain zero stubbed placeholders, and adhere to the server authority model.
