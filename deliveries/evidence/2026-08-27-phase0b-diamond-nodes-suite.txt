WHAT THE 35 ASSERTIONS PIN. Every one compares the node level against the thing
it is supposed to MOVE, never against itself -- the defect class here is a stored
number nobody consults, which looks identical to one that works:
  * level 0 lands exactly on cashBudgetCap -- the Diamond tier begins where the
    Cash tier ends, so no free budget and no stranded budget
  * max level lands exactly on diamondCeiling
  * EVERY level in 1..15 raises by exactly 80 (a node that moved on only some
    levels would still pass a spot check)
  * clamps past max, so a raised ceiling can never exceed maxDiamondCeiling --
    the bound the die validator uses, which would otherwise reject a
    legally-bought die
  * negative / NaN / unknown-shape all floor safely
  * one SlotNodes level adds exactly one slot  <-- the read no code performed
  * ascensions and nodes add together
  * MAX_DIE_SLOTS holds against absurd input, keeping SRS FR-1.1 (1..12) true
  * a NEGATIVE node level floors to 0 and never REMOVES slots -- confiscation is
    the one outcome this must never produce
  * dieSlotCost prices a next slot once a node has raised the cap, so the panel
    cannot hide a slot the player already paid to unlock

NO CONFISCATION IS POSSIBLE BY CONSTRUCTION, and this was the main design risk.
The per-player ceiling gates PURCHASES only. Die validation still uses the
absolute `maxDiamondCeiling()` bound, so an existing die bought under the old
flat 1500 with MassCeiling level 0 keeps every gram it has -- it simply cannot
buy more until the tree catches up. Same rule `AddDieSlot` already follows:
refuse new purchases, never take back what was bought.
