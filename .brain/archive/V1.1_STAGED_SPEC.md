## DESIGN A: BUILD-TIER CALIBRATION
**Problem:** the brain applies production rigor uniformly; a throwaway prototype pays the same ceremony as a flight system. The fast lane only helps tiny diffs, not whole projects.
**Design:**
1. At Gate 0, the intake's INTENT TIER answer (six-pillar question 5) is formalized into a declared, human-confirmed tier recorded in the plan artifact and stamped into the bootloader Section 1 matrix: `PROTOTYPE | INTERNAL | PRODUCTION`.
2. A TIER TABLE (to be added to CHECKLISTS.md when forged) declares per-tier matrix policy: PROTOTYPE may tier-N/A designated line classes (e.g., Matrix D idempotency, Matrix E dependency notes) with a single blanket justification; INTERNAL runs full matrices with relaxed evidence depth; PRODUCTION runs everything at full depth.
3. Never scaled by tier: honesty laws, verdicts, the runtime smoke proof, secret containment, and the governance lock. Speed may be bought; truth may not.
4. TIER DEBT: promoting a project up a tier (prototype -> production) mandates one full-lane re-audit pass (Gates 2–4) over the accumulated codebase before any new feature lands. The shortcut is repaid with interest, visibly.
**Build trigger:** the first project explicitly declared as a prototype, or the first time full ceremony demonstrably blocks a genuinely low-stakes build. Touches: CHECKLISTS (tier table), bootloader Sections 1/6 — human governance key required.

## DESIGN B: SWARM MODE ("ultracode")
**Problem:** the pipeline serializes work that is provably parallel (multi-language localization, disjoint module builds), wasting wall-clock time when host tools support real sub-agents.
**Design:**
1. **Entry criteria (strict):** the task decomposes into >= 3 blocks with PROVABLY DISJOINT file sets (verified by listing each block's files before fan-out), plus explicit operator authorization per run. Coupled blocks void the decomposition: abort fan-out, serialize per Global Law 4.
2. **Fan-out:** the Orchestrator (PM persona) writes one plan-slice per block. Each block gets a Worker + Verifier pair in isolated fresh contexts (host sub-agents; git worktrees where supported), receiving ONLY its plan-slice and its block's files — context slicing is mandatory, not an optimization.
3. **Execution ring:** per pair, the standard loop — construct, mechanically validate, audit — with the Rewind Circuit Breaker (bootloader Section 2.4) capping each pair at three rejection cycles before escalating to the Orchestrator.
4. **Fan-in:** the Orchestrator re-verifies disjointness, merges, runs the full integration test suite plus the runtime smoke, and walks a single consolidated Gate 4 -> 5. The scoreboard records one line per block plus one integration line.
5. **Token guardrails:** dynamic sizing — the Orchestrator must justify every pair spawned (default ceiling: 6 pairs; 1 pair for anything small); tiered model routing where the host supports it (cheap models for mechanical blocks, full reasoning for architecture); no pair ever receives the whole repository.
6. **Known failure modes, designed against:** false independence (caught at fan-out by the file-set proof and at fan-in by re-verification); verifier rubber-stamping (verifiers owe Matrix D evidence per block, same as any Gate 3); merge conflicts (Orchestrator-owned, never resolved by workers).
**Build trigger:** the first real task that passes the entry criteria — a localization pass, a multi-module scaffold, or a disjoint multi-screen UI build. Touches: modes/INDEX.md route + new mode file (agent-writable, additive) — but forging still requires human direction per STATUS above.

## REJECTED FROM THE SOURCE SPEC (recorded so it is not re-litigated)
- Fixed 12+12 agent swarm: replaced by dynamic sizing with justification (the source spec's own optimization #1 concedes this).
- 18-word median responses: outcome-first terseness is house style; hard word caps would strangle verdicts, kill lists, and teaching.
- Stack-specific mandates (Redis, Docker, Bcrypt, Tailwind) in core governance: right ideas, wrong layer — they belong in domain skills born via Skill Genesis on the first project that needs them.
- Fully unattended cross-scope autonomy: unattended-within-approved-plan is the pipeline; unattended-across-ambiguity contradicts HALTED-FOR-CLARIFICATION, which has already prevented real damage twice.
