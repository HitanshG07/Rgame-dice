### L-004: Subject/Session Leakage Silently Inflates ML Evaluation *(harvested 2026-07-15 from child: EnviroNet)*
- **Encountered State:** HAR/pose models on Wi-Fi CSI reported ~85% accuracy; an honest re-evaluation dropped it to 73.0%, then a corrected harness settled at 76.6%.
- **Root Cause Breakdown:** Random train/test splitting put the same subjects (and overlapping sliding windows) in both sets — the model memorized *people*, not the target behavior. A "fixed" LORO harness was itself inflated by two flaws: one test fold contained only a single trivially-separable class (any model scores ~100%), and best-epoch was selected on the test fold.
- **Definitive Fix Action:** For any model that must generalize to unseen entities, evaluation MUST be leave-one-SUBJECT-out (or leave-one-group-out), with early-stopping on a held-out *subject* (never the test fold), pooled metrics across folds, and a check that no fold is degenerate (single-class or trivially separable). A number that drops under honest evaluation is a measurement correction, not a regression — report it as such.

### L-005: Small-Subject-Count Ceiling — Modeling Cannot Buy What Data Lacks *(harvested 2026-07-15 from child: EnviroNet)*
- **Encountered State:** Eight successive modeling improvements (self-supervised pretraining, Doppler-phase features, multi-task heads, longer windows, larger decoders) all plateaued in the same 70–77% band.
- **Root Cause Breakdown:** With only 6 subjects, the binding constraint is dataset diversity, not architecture. SSL/contrastive methods in particular need ~10–100× more data to pay off; below that they underperform simple supervised baselines.
- **Definitive Fix Action:** Before launching a modeling campaign, estimate whether the ceiling is data or model. When repeated honest improvements plateau, STOP and record the dead ends rather than re-attempting variants — collecting more subjects/diversity is the dominant lever. Do not re-run documented dead ends at the same data scale.
- **CORRECTION (2026-07-29, harvested from EnviroNet Phase 8, L-010):** the "collect more SUBJECTS" prioritization here was reached WITHOUT ever measuring cross-environment generalization — `room_id` sat in every cache but appeared in zero lines of the training harness. Data-collection priority INVERTS — new environments now outrank new subjects. The plateau-on-this-dataset finding still stands; the "more subjects" guidance is superseded. Generalizable rule now in `data_science.md` §1: before declaring a ceiling, check every metadata field the harness ignores, and measure cross-environment, not just cross-subject.

### L-015: Per-Entity Game Behaviours Cannot Be Specified Against an Aggregate-State Server Model
- **Encountered State:** Gate 3 rejection of the Ball Escape blueprint, 2026-07-30 (found by the authoring session during verification of the cross-vendor audit, not by the audit itself).

### L-016: A Scalar Optimum Over a Fixed Budget Is Always Solvable — Player Choice Requires Coupling, Not Curve-Shaping
- **Encountered State:** Dice Forge design validation, 2026-08-04. Four pre-code simulations run before any document was written, testing whether a zero-sum "mass budget" spread across die faces produces genuine build diversity or a single dominant strategy.
- **Root Cause Breakdown:** The design assumed that opposing value against probability (`value ∝ mass^α` versus `P(face up) ∝ 1/mass`) would create a trade-off. It does not. Sim 1: the proposed `α=1.5` with `P ∝ 1/m` made FLAT optimal at every shape and every budget — the optimal play was to never use the mechanic at all. A corrected model (`P ∝ (M−m)`, `α=2`) produced an interior optimum, but that optimum sat at ~50% top-share across a 100× budget range (spread 3.3–6.7% for D4/D6/D8) — still one answer. Sim 2: a LINEAR streak bonus could not move it at any strength, because mean streak length varies only ~25% between builds while concentration's raw EV advantage is far larger. Sim 4 variant 1: a flat conditional cross-die bonus could not move it either, and the reason is algebraic — the partner die's trigger probability enters as a CONSTANT multiplier on a term linear in one's own, which is the identical shape that had already failed twice. Three separate "make it a trade-off" attempts failed for one underlying reason: **tuning the shape of a single scalar objective never removes its maximum.**
- **Definitive Fix Action:** Context-dependence must come from COUPLING, not from curve-shaping. Three couplings were measured to work: (1) a COMPOUNDING streak multiplier `(1+b)^s` relocates the optimum (53.1% → 16.7% top-share), though bistably — it becomes real player choice only when streak strength is itself a player-chosen investment, so different players sit on different sides of the cliff; (2) shape choice becomes genuinely contextual under streak pressure — best die is D4 at `b≤0.05` and D20 at `b=0.10`; (3) a cross-die bonus scaling with COMBINED invested mass produces strong coupling (correlation −0.949) — anti-mirroring, where dice specialise into complementary roles. Caveat recorded: co-optimising both dice jointly returns a SYMMETRIC solution, so the puzzle survives only if re-forging is costly enough that players optimise incrementally against dice they already own. GENERALIZABLE RULE: before building any economy or build-craft system, test for a dominant strategy by numerically optimising the player's objective across the full parameter range. If one distribution wins everywhere, the mechanic is decoration regardless of how interesting it reads on paper. Cost here: four simulations, roughly two hours, entirely pre-code. — Last Verified: 2026-08-04

### L-017: A Correct Structural Prediction Is Worth More Than a Re-Run — But Only If Stated Before the Numbers
- **Encountered State:** Dice Forge simulation 4, 2026-08-04.
- **Root Cause Breakdown:** Two prior cross-die models (sims 2 and 3) failed, and in both cases the failure was in the AGENT'S MODEL, not the game design — the optimiser had no trade-off to resolve because the element's benefit had no competing cost. Both were reported as invalid tests rather than as evidence against the mechanic, which was the correct call: a broken test that returns a negative result is not a negative result. On the third attempt the algebraic reason for the failure was identified and WRITTEN DOWN BEFORE running (partner trigger probability enters as a constant multiplier), then confirmed numerically. That prediction is what justified testing a second variant in the same run instead of burning another cycle.
- **Definitive Fix Action:** When a simulation returns a flat/null result, first ask whether the MODEL contained a trade-off at all — an optimiser with a free lunch always takes it, and that says nothing about the design. State the structural prediction before running, so a confirmed prediction can be distinguished from a lucky fit. Never report a modelling error as a design finding; the honest verdict is "this test was invalid," which is what was reported twice here. — Last Verified: 2026-08-04

### L-024: A Test That Only Feeds Clean Numbers Cannot Find a Rounding Bug

### L-029: A Unit Carried Across a Coordinate-System Change Is Silently Wrong, Not Loudly Wrong
- **Encountered State:** Dice Forge Block 4, 2026-08-09. ### L-032: A Fallback Constant in a Grant Path Is a Wrong Answer Delivered Confidently
- **Encountered State:** Dice Forge Block 5, 2026-08-11. `PurchaseService.applyGrant`'s TimeSkip branch computed `payout = seconds * rate` and then, when that came out non-positive, substituted `payout = 1000 -- baseline floor so time skip never credits zero`. `rate` is the player's `Vault.AvgIncomePerSec`, which is ZERO until they have actually earned, and `getStatus` returns nil outright when there is no profile -- so BOTH ordinary cases fell to the constant. The function then returned success, the receipt handler answered `PurchaseGranted`, and Roblox kept the money and stopped retrying. A player earning 50k/sec buys "24 hours of offline earnings" and irreversibly receives 1,000.
- **Root Cause Breakdown:** The fallback was written to prevent an embarrassing zero, and it converted a RECOVERABLE failure into an UNRECOVERABLE one. Returning nothing would have answered NotProcessedYet, kept the receipt alive, and granted correctly on the platform's own retry once the player had played. Instead the code asserted an answer it had no basis for. The deeper error is the instinct that a grant path should always produce a number: in a payment flow, "I cannot compute this yet" is a legitimate and SAFE outcome, and dressing it as a small success destroys the retry that would have fixed it. Note the comment DEFENDED the behaviour, so a reviewer reading for intent would have agreed with it.
- **Definitive Fix Action:** In any path that grants purchased value, NEVER substitute a default for a quantity that could not be computed -- return failure and let the platform's retry semantics do their job. Reserve fallbacks for DISPLAY, where a wrong number is cosmetic, and forbid them in grant, credit and entitlement paths where a wrong number is a transaction. Review rule: every literal appearing after a `<= 0` or `== nil` guard inside a grant function is a finding until proven display-only. Related: [[L-027]] -- both are cases where the code's shape looked complete while the behaviour was absent or wrong. -- Last Verified: 2026-08-11

### L-033: A Handler That Reports Success It Did Not Deliver Is Worse Than a Missing One
- **Encountered State:** Dice Forge Block 5/6, 2026-08-11. Four remote handlers passed every structural check and did nothing. `ClaimQuest` and `ClaimChest` were literally `return true, nil`. `SetAutoRoll` validated its boolean, checked gamepass ownership, then DISCARDED the value -- the toggle was inert and the server never auto-rolled for anyone, while the Auto-Roll gamepass was on sale against it. `claimGroupReward` carried the comment `-- Verified server-side` directly above code that verified nothing: `GroupService` was required at the top of the file and never called, so any player could claim 250 Gems and 15 Diamonds by invoking the remote once. A prior report recorded all sixteen remotes as "100% registered", which was true and meaningless.
- **Root Cause Breakdown:** Two failures that compound. (1) REGISTERED IS NOT IMPLEMENTED. Every producer-direction check to date asked "does a handler exist for this remote?" -- a question all four passed. Nothing asked "does the handler change state?" (2) SUCCESS WAS REPORTED ANYWAY, and because these handlers were wrapped in `announcing`, a StateSync push followed showing UNCHANGED state. The player saw a claimed quest and no reward: the game actively told them their reward had been taken. A missing handler produces an error the player can report; a lying handler produces silent loss that looks like their own mistake. Separately, `-- Verified server-side` is the sharpest instance of a related failure: a comment asserting a control that does not exist defeats the reviewer who reads for INTENT, which is exactly what a Gate 3 cognitive audit does.
- **Definitive Fix Action:** Extend the producer-direction sweep from EXISTENCE to EFFECT: for every remote, the evidence is the named state mutation it performs -- a handler with no `mutate`, no credit and no service delegation is a FINDING regardless of what it returns. Treat any handler body under roughly four lines that neither delegates nor mutates as a stub until shown otherwise. And treat a comment asserting a control ("verified", "validated", "checked") as a claim needing the same evidence as a test: grep for the call it names, and if it is absent the comment is a defect of HIGHER severity than the missing control, because it stops anyone else looking. Related: [[L-027]] (specified-but-unimplemented rows), [[L-021]] (citations must quote, not paraphrase). -- Last Verified: 2026-08-11

### L-034: A Balance Requirement Is a Property of the Numbers and No Code Test Can See It
- **Encountered State:** Dice Forge, 2026-08-11. SRS FR-6.3 states that no die shape may dominate at every Streak Strength `b`, naming the violation explicitly: "a build where one shape wins at every `b` is a balance defect." A sweep over eight values of `b` returned the D20 EIGHT TIMES OUT OF EIGHT. The cause was structural: `defaultBudget` scaled with face count (D2 = 20 through D20 = 200), and because payout is superlinear in mass (alpha = 2), a larger budget is strictly better -- so face count, the variable the entire shape design rests on, was irrelevant. The build had shipped this way through five audit rounds, 18 green suites and 3,448 passing assertions.
- **Root Cause Breakdown:** Every existing test asked whether the CODE was correct. This requirement is about whether the NUMBERS are correct, and the two are orthogonal -- sampling, payout and streak were all provably right, and faithfully computed a dominated game. Nothing failed, because nothing was wrong in the sense the suites could express. Compounding it, `DiceCatalog`'s own header admitted the crossover was "NOT YET VERIFIED" and pointed at a roadmap prompt not yet reached: the gap was DOCUMENTED and therefore felt handled, which is its own hazard -- a known-unknown written into the file it affects reads as a caveat rather than an open defect. And per-shape budgets of 10 mass per face look deliberate row by row; the defect exists only in the RELATIONSHIP between rows, which inspection does not surface.
- **Definitive Fix Action:** Any requirement phrased over a SPACE of configurations -- "no X dominates", "the curve must cross", "no dominant strategy" -- gets its own executable sweep in the standard suite, run every pass, evaluated against the SHIPPING constants and never a fixture (a balance test carrying its own numbers tests nothing). Assert the structural CAUSE alongside the property so a future failure reports why, not merely that the sweep broke -- here, that the budget is identical across shapes. State the limits inside the suite: passing proves a crossover EXISTS, not that it sits anywhere sensible, which stays a design judgement. Corollary: a documented "not yet verified" in a source file is an open defect with a deadline, not a caveat -- it belongs in a failing test or a roadmap item, never in a comment. Related: [[L-031]] (the check could not reach where the defect lived), [[L-016]] (the simulations that established these mechanics). -- Last Verified: 2026-08-11
