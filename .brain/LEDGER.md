### L-004: Subject/Session Leakage Silently Inflates ML Evaluation *(harvested 2026-07-15 from child: EnviroNet)*
- **Encountered State:** HAR/pose models on Wi-Fi CSI reported ~85% accuracy; an honest re-evaluation dropped it to 73.0%, then a corrected harness settled at 76.6%.
- **Root Cause Breakdown:** Random train/test splitting put the same subjects (and overlapping sliding windows) in both sets — the model memorized *people*, not the target behavior. A "fixed" LORO harness was itself inflated by two flaws: one test fold contained only a single trivially-separable class (any model scores ~100%), and best-epoch was selected on the test fold.
- **Definitive Fix Action:** For any model that must generalize to unseen entities, evaluation MUST be leave-one-SUBJECT-out (or leave-one-group-out), with early-stopping on a held-out *subject* (never the test fold), pooled metrics across folds, and a check that no fold is degenerate (single-class or trivially separable). A number that drops under honest evaluation is a measurement correction, not a regression — report it as such.

### L-005: Small-Subject-Count Ceiling — Modeling Cannot Buy What Data Lacks *(harvested 2026-07-15 from child: EnviroNet)*
- **Encountered State:** Eight successive modeling improvements (self-supervised pretraining, Doppler-phase features, multi-task heads, longer windows, larger decoders) all plateaued in the same 70–77% band.
- **Root Cause Breakdown:** With only 6 subjects, the binding constraint is dataset diversity, not architecture. SSL/contrastive methods in particular need ~10–100× more data to pay off; below that they underperform simple supervised baselines.
- **Definitive Fix Action:** Before launching a modeling campaign, estimate whether the ceiling is data or model. When repeated honest improvements plateau, STOP and record the dead ends rather than re-attempting variants — collecting more subjects/diversity is the dominant lever. Do not re-run documented dead ends at the same data scale.
- **CORRECTION (2026-07-29, harvested from EnviroNet Phase 8, L-010):** the "collect more SUBJECTS" prioritization here was reached WITHOUT ever measuring cross-environment generalization — `room_id` sat in every cache but appeared in zero lines of the training harness. Leave-one-ROOM-out then showed an ~36-point cross-room gap (80.5% within-room → ~44% cross-room) versus a far smaller cross-subject gap: the models were substantially learning the ROOMS. Data-collection priority INVERTS — new environments now outrank new subjects. The plateau-on-this-dataset finding still stands; the "more subjects" guidance is superseded. Generalizable rule now in `data_science.md` §1: before declaring a ceiling, check every metadata field the harness ignores, and measure cross-environment, not just cross-subject.

### L-015: Per-Entity Game Behaviours Cannot Be Specified Against an Aggregate-State Server Model
- **Encountered State:** Gate 3 rejection of the Ball Escape blueprint, 2026-07-30 (found by the authoring session during verification of the cross-vendor audit, not by the audit itself).

### L-016: A Scalar Optimum Over a Fixed Budget Is Always Solvable — Player Choice Requires Coupling, Not Curve-Shaping
- **Encountered State:** Dice Forge design validation, 2026-08-04. Four pre-code simulations run before any document was written, testing whether a zero-sum "mass budget" spread across die faces produces genuine build diversity or a single dominant strategy.
- **Root Cause Breakdown:** The design assumed that opposing value against probability (`value ∝ mass^α` versus `P(face up) ∝ 1/mass`) would create a trade-off. It does not. Sim 1: the proposed `α=1.5` with `P ∝ 1/m` made FLAT optimal at every shape and every budget — the optimal play was to never use the mechanic at all. A corrected model (`P ∝ (M−m)`, `α=2`) produced an interior optimum, but that optimum sat at ~50% top-share across a 100× budget range (spread 3.3–6.7% for D4/D6/D8) — still one answer. Sim 2: a LINEAR streak bonus could not move it at any strength, because mean streak length varies only ~25% between builds while concentration's raw EV advantage is far larger. Sim 4 variant 1: a flat conditional cross-die bonus could not move it either, and the reason is algebraic — the partner die's trigger probability enters as a CONSTANT multiplier on a term linear in one's own, which is the identical shape that had already failed twice. Three separate "make it a trade-off" attempts failed for one underlying reason: **tuning the shape of a single scalar objective never removes its maximum.**
- **Definitive Fix Action:** Context-dependence must come from COUPLING, not from curve-shaping. Three couplings were measured to work: (1) a COMPOUNDING streak multiplier `(1+b)^s` relocates the optimum (53.1% → 16.7% top-share), though bistably — it becomes real player choice only when streak strength is itself a player-chosen investment, so different players sit on different sides of the cliff; (2) shape choice becomes genuinely contextual under streak pressure — best die is D4 at `b≤0.05` and D20 at `b=0.10`; (3) a cross-die bonus scaling with COMBINED invested mass produces strong coupling (correlation −0.949) — anti-mirroring, where dice specialise into complementary roles. Caveat recorded: co-optimising both dice jointly returns a SYMMETRIC solution, so the puzzle survives only if re-forging is costly enough that players optimise incrementally against dice they already own. GENERALIZABLE RULE: before building any economy or build-craft system, test for a dominant strategy by numerically optimising the player's objective across the full parameter range. If one distribution wins everywhere, the mechanic is decoration regardless of how interesting it reads on paper. Cost here: four simulations, roughly two hours, entirely pre-code. — Last Verified: 2026-08-04

### L-017: A Correct Structural Prediction Is Worth More Than a Re-Run — But Only If Stated Before the Numbers
- **Encountered State:** Dice Forge simulation 4, 2026-08-04.
- **Root Cause Breakdown:** Two prior cross-die models (sims 2 and 3) failed, and in both cases the failure was in the AGENT'S MODEL, not the game design — the optimiser had no trade-off to resolve because the element's benefit had no competing cost. Both were reported as invalid tests rather than as evidence against the mechanic, which was the correct call: a broken test that returns a negative result is not a negative result. On the third attempt the algebraic reason for the failure was identified and WRITTEN DOWN BEFORE running (partner trigger probability enters as a constant multiplier), then confirmed numerically. That prediction is what justified testing a second variant in the same run instead of burning another cycle.
- **Definitive Fix Action:** When a simulation returns a flat/null result, first ask whether the MODEL contained a trade-off at all — an optimiser with a free lunch always takes it, and that says nothing about the design. State the structural prediction before running, so a confirmed prediction can be distinguished from a lucky fit. Never report a modelling error as a design finding; the honest verdict is "this test was invalid," which is what was reported twice here. — Last Verified: 2026-08-04

### L-022: MCP `execute_luau` Does Not Share the Running VM's Module Cache
- **Encountered State:** Block 3 verification, 2026-08-06. With the game running and a real player joined, an introspection via the Studio MCP server's `execute_luau` (`datamodel_type: "Server"`) reported `PlayerProfile.isActive(player) == false` and `PlayerProfile.get(player) == nil` — a player seated in a live session with no profile and no kick, which reads as a fail-OPEN on threat T-10. I reported it as a defect and restructured `ServerBootstrap` in response. **The observation was false.** The server's own in-VM print (`[Bootstrap] admitted UserId=...`) showed the profile had loaded correctly all along.
- **Root Cause Breakdown:** Each `execute_luau` invocation re-executes `require`, receiving a FRESH module instance with empty upvalues rather than the instance the running server holds. Proved directly: a counter set on the `PlayerProfile` module table in one call read back as 1, not 2, in the next. ## Third-Party Dependency & API Quirks
### L-002: Camera2 Extension Session Viewfinder Aspect Resolution IllegalArgumentException *(harvested 2026-07-08 from child: renocore-camera; generalized into `.brain/skills/android_camera.md` and the Matrix D code-to-world contract)*
- **Encountered State:** Phase 2 Capture Engine Verification & Viewfinder Launch
- **Root Cause Breakdown:** On Oppo/ColorOS devices (and standard Android 12+ Camera Extension HALs), a `CameraExtensionSession` preview surface resolution must exactly match one of the supported resolutions returned by `CameraExtensionCharacteristics.getExtensionSupportedSizes(extensionType, SurfaceHolder::class.java)`. Configuring a SurfaceView with full-screen bounds (e.g. `1080x2193` in Compose layout) causes the HAL to throw `java.lang.IllegalArgumentException: Repeating request surface size ... not supported!`, resulting in session configuration failure and a black screen.
- **Definitive Fix Action:** Call `surfaceHolder.setFixedSize(width, height)` dynamically using an optimal supported preview resolution resolved from `CameraExtensionCharacteristics.getExtensionSupportedSizes` or `SCALER_STREAM_CONFIGURATION_MAP` fallback. This sets the internal graphics buffer size to a supported standard size while letting the Android Window Manager automatically upscale or downscale it to fit the Compose UI container layout bounds.

### L-010: OEM HAL SIGSEGV on Concurrent Max-Resolution + Video *(harvested 2026-07-17 from child: renocore-camera, Phase 3 — final harvest before project retirement)*
- **Encountered State:** Phase 3 video verification on Oppo/MediaTek — fatal crash when video recording started with high-res capture configured.
- **Root Cause Breakdown:** The MediaTek/Oppo ISP streaming pipeline (`libmtkcam.featurepipe.streaming.so`) cannot multiplex an unbinned max-resolution sensor stream (`SENSOR_PIXEL_MODE_MAXIMUM_RESOLUTION`) and a `MediaRecorder` video encoder on the same logical session; the combination throws `SIGSEGV`. Calling `OutputConfiguration.setPhysicalCameraId()` on the video surface compounds it.
- **Definitive Fix Action:** In video mode, force high-res off (fall back to binned) before resolving the `ImageReader` size, and never set a physical camera ID on the video `OutputConfiguration`. More broadly on OEM camera stacks: never assume two heavyweight hardware pipelines (max-res stills + video encode) can share one session — query and degrade. Generalized into `.brain/skills/android_camera.md` §5, which also carries the unresolved mode-switch-freeze hazard and the video-concurrency discipline from this project. — Last Verified: 2026-07-17

### L-011: A Real Number Can Carry a False Causal Claim Past a One-Directional Tripwire *(harvested 2026-07-29 from child: EnviroNet, Phase 8)*
- **Encountered State:** A genuinely one-variable experiment produced a "+2.83 pt" gain that passed the project's own integrity guard and was recorded as confirmed — then a third-pass Gate 3 audit withdrew it.
- **Root Cause Breakdown:** Two distinct integrity failures, same category as L-006 but a different shape. (1) The significance was computed at the wrong UNIT — pooled window-level McNemar over 8705 correlated windows from 172 runs looked decisive, but at the exchangeable unit (6 subjects) t(5)=0.77, not significant; removing one subject flipped the pooled delta to ~0. (2) The verdict script applied a fold-spread check only to the `SIGN_HURTS` branch, not `SIGN_HELPS` — asymmetric skepticism let a real number acquire an unsupported mechanism ("it helps hand") that per-class analysis falsified (it hurt hand, helped knee/walk).
- **Definitive Fix Action:** Apply the SAME statistical scrutiny to welcome and unwelcome results; measure significance at the exchangeable unit, never at pooled correlated samples; a correct number never validates a mechanism without per-class/per-fold checks; and verify the code computed the named quantity before recording any dead end. Generalized into `.brain/skills/data_science.md` §1. Note: the brain's tripwire firing on the earlier fabricated 80.54% (L-006 class) AND this third-pass withdrawal are both the honesty layer working — the second catch proves it scrutinizes its own welcome results, not only its failures. — Last Verified: 2026-07-29
