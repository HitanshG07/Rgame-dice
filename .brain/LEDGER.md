### L-004: Subject/Session Leakage Silently Inflates ML Evaluation *(harvested 2026-07-15 from child: EnviroNet)*
- **Encountered State:** HAR/pose models on Wi-Fi CSI reported ~85% accuracy; an honest re-evaluation dropped it to 73.0%, then a corrected harness settled at 76.6%.
- **Root Cause Breakdown:** Random train/test splitting put the same subjects (and overlapping sliding windows) in both sets — the model memorized *people*, not the target behavior. A "fixed" LORO harness was itself inflated by two flaws: one test fold contained only a single trivially-separable class (any model scores ~100%), and best-epoch was selected on the test fold.
- **Definitive Fix Action:** For any model that must generalize to unseen entities, evaluation MUST be leave-one-SUBJECT-out (or leave-one-group-out), with early-stopping on a held-out *subject* (never the test fold), pooled metrics across folds, and a check that no fold is degenerate (single-class or trivially separable). A number that drops under honest evaluation is a measurement correction, not a regression — report it as such.

### L-005: Small-Subject-Count Ceiling — Modeling Cannot Buy What Data Lacks *(harvested 2026-07-15 from child: EnviroNet)*
- **Encountered State:** Eight successive modeling improvements (self-supervised pretraining, Doppler-phase features, multi-task heads, longer windows, larger decoders) all plateaued in the same 70–77% band.
- **Root Cause Breakdown:** With only 6 subjects, the binding constraint is dataset diversity, not architecture. SSL/contrastive methods in particular need ~10–100× more data to pay off; below that they underperform simple supervised baselines.
- **Definitive Fix Action:** Before launching a modeling campaign, estimate whether the ceiling is data or model. When repeated honest improvements plateau, STOP and record the dead ends rather than re-attempting variants — collecting more subjects/diversity is the dominant lever. Do not re-run documented dead ends at the same data scale.
- **CORRECTION (2026-07-29, harvested from EnviroNet Phase 8, L-010):** the "collect more SUBJECTS" prioritization here was reached WITHOUT ever measuring cross-environment generalization — `room_id` sat in every cache but appeared in zero lines of the training harness. Data-collection priority INVERTS — new environments now outrank new subjects. The plateau-on-this-dataset finding still stands; the "more subjects" guidance is superseded. Generalizable rule now in `data_science.md` §1: before declaring a ceiling, check every metadata field the harness ignores, and measure cross-environment, not just cross-subject.

### L-015: Per-Entity Game Behaviours Cannot Be Specified Against an Aggregate-State Server Model
- **Encountered State:** Gate 3 rejection of the Ball Escape blueprint, 2026-07-30 (found by the authoring session during verification of the cross-vendor audit, not by the audit itself).

### L-016: A Scalar Optimum Over a Fixed Budget Is Always Solvable — Player Choice Requires Coupling, Not Curve-Shaping
- **Encountered State:** Dice Forge design validation, 2026-08-04. Four pre-code simulations run before any document was written, testing whether a zero-sum "mass budget" spread across die faces produces genuine build diversity or a single dominant strategy.
- **Root Cause Breakdown:** The design assumed that opposing value against probability (`value ∝ mass^α` versus `P(face up) ∝ 1/mass`) would create a trade-off. It does not. Sim 1: the proposed `α=1.5` with `P ∝ 1/m` made FLAT optimal at every shape and every budget — the optimal play was to never use the mechanic at all. A corrected model (`P ∝ (M−m)`, `α=2`) produced an interior optimum, but that optimum sat at ~50% top-share across a 100× budget range (spread 3.3–6.7% for D4/D6/D8) — still one answer. Sim 2: a LINEAR streak bonus could not move it at any strength, because mean streak length varies only ~25% between builds while concentration's raw EV advantage is far larger. Sim 4 variant 1: a flat conditional cross-die bonus could not move it either, and the reason is algebraic — the partner die's trigger probability enters as a CONSTANT multiplier on a term linear in one's own, which is the identical shape that had already failed twice. Three separate "make it a trade-off" attempts failed for one underlying reason: **tuning the shape of a single scalar objective never removes its maximum.**
- **Definitive Fix Action:** Context-dependence must come from COUPLING, not from curve-shaping. Three couplings were measured to work: (1) a COMPOUNDING streak multiplier `(1+b)^s` relocates the optimum (53.1% → 16.7% top-share), though bistably — it becomes real player choice only when streak strength is itself a player-chosen investment, so different players sit on different sides of the cliff; (2) shape choice becomes genuinely contextual under streak pressure — best die is D4 at `b≤0.05` and D20 at `b=0.10`; (3) a cross-die bonus scaling with COMBINED invested mass produces strong coupling (correlation −0.949) — anti-mirroring, where dice specialise into complementary roles. Caveat recorded: co-optimising both dice jointly returns a SYMMETRIC solution, so the puzzle survives only if re-forging is costly enough that players optimise incrementally against dice they already own. GENERALIZABLE RULE: before building any economy or build-craft system, test for a dominant strategy by numerically optimising the player's objective across the full parameter range. If one distribution wins everywhere, the mechanic is decoration regardless of how interesting it reads on paper. Cost here: four simulations, roughly two hours, entirely pre-code. — Last Verified: 2026-08-04

### L-017: A Correct Structural Prediction Is Worth More Than a Re-Run — But Only If Stated Before the Numbers
- **Encountered State:** Dice Forge simulation 4, 2026-08-04.
- **Root Cause Breakdown:** Two prior cross-die models (sims 2 and 3) failed, and in both cases the failure was in the AGENT'S MODEL, not the game design — the optimiser had no trade-off to resolve because the element's benefit had no competing cost. Both were reported as invalid tests rather than as evidence against the mechanic, which was the correct call: a broken test that returns a negative result is not a negative result. On the third attempt the algebraic reason for the failure was identified and WRITTEN DOWN BEFORE running (partner trigger probability enters as a constant multiplier), then confirmed numerically. That prediction is what justified testing a second variant in the same run instead of burning another cycle.
- **Definitive Fix Action:** When a simulation returns a flat/null result, first ask whether the MODEL contained a trade-off at all — an optimiser with a free lunch always takes it, and that says nothing about the design. State the structural prediction before running, so a confirmed prediction can be distinguished from a lucky fit. Never report a modelling error as a design finding; the honest verdict is "this test was invalid," which is what was reported twice here. — Last Verified: 2026-08-04

### L-024: A Test That Only Feeds Clean Numbers Cannot Find a Rounding Bug

### L-029: A Unit Carried Across a Coordinate-System Change Is Silently Wrong, Not Loudly Wrong
- **Encountered State:** Dice Forge Block 4, 2026-08-09. ### L-032: A Fallback Constant in a Grant Path Is a Wrong Answer Delivered Confidently
- **Encountered State:** Dice Forge Block 5, 2026-08-11. `PurchaseService.applyGrant`'s TimeSkip branch computed `payout = seconds * rate` and then, when that came out non-positive, substituted `payout = 1000 -- baseline floor so time skip never credits zero`. `rate` is the player's `Vault.AvgIncomePerSec`, which is ZERO until they have actually earned, and `getStatus` returns nil outright when there is no profile -- so BOTH ordinary cases fell to the constant. The function then returned success, the receipt handler answered `PurchaseGranted`, and Roblox kept the money and stopped retrying. A player earning 50k/sec buys "24 hours of offline earnings" and irreversibly receives 1,000.
- **Root Cause Breakdown:** The fallback was written to prevent an embarrassing zero, and it converted a RECOVERABLE failure into an UNRECOVERABLE one. Returning nothing would have answered NotProcessedYet, kept the receipt alive, and granted correctly on the platform's own retry once the player had played. Instead the code asserted an answer it had no basis for. The deeper error is the instinct that a grant path should always produce a number: in a payment flow, "I cannot compute this yet" is a legitimate and SAFE outcome, and dressing it as a small success destroys the retry that would have fixed it. Note the comment DEFENDED the behaviour, so a reviewer reading for intent would have agreed with it.
- **Definitive Fix Action:** In any path that grants purchased value, NEVER substitute a default for a quantity that could not be computed -- return failure and let the platform's retry semantics do their job. Reserve fallbacks for DISPLAY, where a wrong number is cosmetic, and forbid them in grant, credit and entitlement paths where a wrong number is a transaction. Review rule: every literal appearing after a `<= 0` or `== nil` guard inside a grant function is a finding until proven display-only. Related: [[L-027]] -- both are cases where the code's shape looked complete while the behaviour was absent or wrong. -- Last Verified: 2026-08-11

### L-034: A Balance Requirement Is a Property of the Numbers and No Code Test Can See It
- **Encountered State:** Dice Forge, 2026-08-11. SRS FR-6.3 states that no die shape may dominate at every Streak Strength `b`, naming the violation explicitly: "a build where one shape wins at every `b` is a balance defect." A sweep over eight values of `b` returned the D20 EIGHT TIMES OUT OF EIGHT. The cause was structural: `defaultBudget` scaled with face count (D2 = 20 through D20 = 200), and because payout is superlinear in mass (alpha = 2), a larger budget is strictly better -- so face count, the variable the entire shape design rests on, was irrelevant. The build had shipped this way through five audit rounds, 18 green suites and 3,448 passing assertions.
- **Root Cause Breakdown:** Every existing test asked whether the CODE was correct. This requirement is about whether the NUMBERS are correct, and the two are orthogonal -- sampling, payout and streak were all provably right, and faithfully computed a dominated game. Nothing failed, because nothing was wrong in the sense the suites could express. ### L-052: Made Visible Before Positioned -- One Frame Is Enough to Look Broken
- **Encountered State:** Dice Forge, 2026-08-15. The operator reported dice "breaking and deforming and then falling", with screenshots of coins as fragments mid-flight. Sampling each die's pivot every frame found no deformation at all -- parts were perfectly rigid, drift 0.00000 studs across 165 parts -- but two position discontinuities of ~11 studs per roll: `t=0.050 pos=(-2.44,0.37,7.08)` at rest, `t=0.118 pos=(0.00,0.00,0.00)` AT THE ORIGIN, `t=0.183 pos=(4.72,5.88,-10.87)` at the throw start. Two separate code paths made a die visible before positioning it: `applyModel` parented a fresh clone (a clone sits at its authored origin and `Parent` renders it immediately), and `measureSitHeight` posed the model with a rotation carrying no translation -- also the origin -- one frame before the flight began. - **Root Cause Breakdown:** In Roblox, parenting an Instance or setting `Visible` takes effect on the CURRENT frame, while any positioning done from `RenderStepped` lands on the NEXT one. One frame sounds negligible and is not: at 60fps it is a hard cut to a wrong position and back, which the eye reads as tearing, fragmenting, or an element flying in from off-screen. It is also invisible to every static check and to most instrumentation, because the object's END state is always correct -- the position sampled a frame later is right, the geometry is rigid, and no error is logged. It surfaces only in per-frame sampling, or to a human watching.
- **Definitive Fix Action:** Position before revealing, always, and treat the two as one operation. For a 3D model: `PivotTo` somewhere off-camera BEFORE assigning `Parent`, never after. For a GUI element: do not let a visibility flag be driven by intent alone -- gate it on having been positioned at least once, and clear that gate when the element is released. ### L-053: A Floor Set Below One Sum Is Not Below Another -- Solve the Threshold, Do Not Guess the Direction
- **Encountered State:** Dice Forge, 2026-08-15. VIP's vault capacity FLOOR was 24h while every other capacity source combined reached 20h -- base 4 + Cash upgrades 4 + Gems 8 + Premium 4 -- so the floor silently swallowed the entire Gem purchase. Measured both ways: a VIP player with 0 Gem-hours had 24h capacity, and with 8 Gem-hours also had 24h. They had been charged 40 Gems for zero capacity, and the VAULT panel then displayed "+8h of that is Gem-bought", crediting the purchase with an effect it did not have. The operator caught it from the panel alone: "how does this work if its still 24hrs". The first correction lowered the floor to 16h, which is below the 20h maximum and therefore looked right -- and changed nothing, because the binding comparison is not against the maximum. It is against what a VIP player reaches WITHOUT Gems: base 4h + Gems 8h = 12h. Both 16h and 12h still absorb the purchase; only below 12h does it contribute.
- **Root Cause Breakdown:** A `math.max` floor interacts with a SUM, and reasoning about it as "lower the floor below the total" picks the wrong comparison. The quantity that matters is what the floor competes against for the specific player being considered -- here the worst case is a VIP player with no upgrades and no Premium, whose alternative is only base plus the purchasable term. The 16h attempt was a plausible number chosen by direction of travel rather than by solving the inequality, which is the same shape of error as tuning a constant until it looks better instead of deriving the value the requirement implies. Compounding it, the panel's honesty fix then had its own version: `buyableHours <= 0` has two causes that mean OPPOSITE things -- at the purchase cap (the Gems worked, there is simply nothing left to buy) versus absorbed by a floor (the Gems did nothing) -- and reading it as only the second told a player with a genuinely working +8h that it was "not adding to it".
- **Definitive Fix Action:** When a floor, cap or clamp interacts with a sum, WRITE OUT the comparison it actually performs and solve for the threshold, then print the table of candidate values and their outcomes before choosing one. Three lines of arithmetic settled here what two guesses could not. Second, and more general: a monetised term that can be silently absorbed by another entitlement is a "sold something that does nothing" defect, not a balance nuance -- the purchase path must REFUSE when it cannot help, and the readout must never credit a purchase with an effect the arithmetic did not produce. Third: when a single boolean has two causes with opposite meanings, do not let a display branch on it -- distinguish them at the source. Related: [[L-025]] (state a rule once, executably -- the "24h" in the upsell string was a second copy of the floor and would have advertised capacity the pass no longer grants), [[L-039]] (a value with no honest display cannot be observed failing). -- Last Verified: 2026-08-15

### L-054: A Test That Needs a Capability the Test Thread Lacks Takes Down Every Assertion Beside It
- **Encountered State:** Dice Forge, 2026-08-15. A new check swept every client view module for emoji by reading `LuaSourceContainer.Source`. Third: when a check can only run in a privileged context, keep a second path that runs where the privilege exists -- here the same scan is reproducible from the shell against any commit, so the rule is still enforced even when the suite skips it. ### L-055: Rebuilding the Rows and Leaving the Container Is Half a Layout, and the Half That Remains Decides
- **Encountered State:** Dice Forge, 2026-08-15. The FORGE's face rows were rebuilt onto pixel-based layout primitives while the panel's SECTIONS kept their original scale offsets -- tab strip `0.062` high, readout `0.125` down, face list `0.66` tall, action bar at `0.875`. Measured on a 276px-tall viewport: the tab strip rendered ELEVEN pixels tall, and the action bar sat 22px BELOW the panel body with its primary FORGE button outside the card entirely. Every row inside was correct; the panel was still broken. Two other defects rode along in the same rebuild -- `moveLeftC`/`moveRightC` no longer existed once the arrows became `actionButton`s, so every snapshot raised "attempt to index nil with 'Visible'", and two `setEnabled` calls on `actionButton`s survived silently because that function does not throw on the wrong widget type, it just does nothing.
- **Root Cause Breakdown:** Mixing coordinate systems is not a cosmetic inconsistency, it is a dependency: a scale fraction only means what its author intended while the parent's height is what the author assumed. Converting the leaves to pixels while the branches stayed fractional guaranteed the two would disagree the moment any ancestor's sizing changed -- and it HAD changed, in the same pass, three files away. The nil-index and the silent no-op are the same lesson in a different register: a rebuild that swaps one builder for another leaves call sites referring to the old shape, and only SOME of them fail loudly. The ones that fail loudly are found by the console in seconds; the ones that fail silently are found by nothing at all, and a grep for the removed NAMES caught what a grep for errors could not.
- **Definitive Fix Action:** When converting a surface to a layout system, convert the whole path from the panel root to the leaf in one pass, or convert none of it -- and declare the section heights ONCE as named constants read by every band, so the bands cannot drift apart (two copies of `34` appeared within minutes of writing the first). Anchor bottom-fixed chrome to the bottom edge, never to a fraction. Second: after ANY builder swap, mechanically cross-check every call site against the builder that produced its widget -- match variable to constructor, not by eye -- because setters that no-op on the wrong type are invisible to tests, to the console, and to a screenshot. Third: read the CONSOLE after the suite, not just the suite's verdict. This run was green at 21/21 while emitting `applyState failed` twice per snapshot; a passing suite says nothing about the code paths the suite never enters. Related: [[L-025]] (declare a shared value once), [[L-042]] (a setter reaching into a builder's internals by the wrong contract), [[L-051]] (the screenshot is what settled it). -- Last Verified: 2026-08-15

### L-056: Five Attempts Failed Because Nobody Measured Which Part Was Small
- **Encountered State:** Dice Forge, 2026-08-15. Sub-pixel shearing on the dice survived four attempts across two sessions, each of which modified the NUMERAL geometry and each of which produced blank or cube-like dice (L-051). The fifth attempt began by measuring the built solids instead of theorising, and the answer was immediate: numeral strokes measure 0.039-0.061 studs, which projects to 2-3 px through the board camera and was never the problem. The `ChamferWedge` parts on the D10 and D14 measured **0.0097** -- 0.50 px at 720p and 0.25 px with seven dice on the felt, permanently below one pixel at every supported resolution. The defect had been in a different class of part the whole time, and four rounds of increasingly elaborate glyph surgery could never have reached it.
- **Root Cause Breakdown:** The first attempt guessed "the thin things are the numerals" from a screenshot, and every subsequent attempt inherited that premise without re-testing it -- each new metric was written to explain why the PREVIOUS fix failed, so all four measured properties of the numerals and none ever asked which part was actually smallest. One `min(Size.X, Size.Y, Size.Z)` sweep over the twelve models, grouped by part name, would have answered it in one call at any point. The geometric cause, once located, was ordinary: a chamfer bridges two inset faces, so its width is set by how sharply they meet, and the D10/D14 kite facets meet at very shallow angles around the equator -- leaving nothing to bridge. Two further mistakes followed inside this session and are the reason the entry is worth keeping: the filter was FIRST placed in the edge-bridge loop, where it changed literally nothing (caught only because the before/after comparison was run rather than assumed), and when moved to the triangle splitter it was applied to the isosceles branch alone, leaving 10 slivers on the D10 and 7 on the D14 that a second measurement found.
- **Definitive Fix Action:** Before fixing a "things are too small" defect, ENUMERATE the small things and sort them -- by part name, by measured minimum axis, projected into the units the viewer experiences (pixels, not studs). The population that is actually offending is frequently not the one the symptom suggests, and this costs one query against an assumption that cost four rounds. Second: filter degenerate geometry by SKIPPING it, never by resizing it to clear a threshold -- a part below the visible floor contributes nothing when it works, so removing it is free, whereas inflating it deforms the silhouette (which is precisely how the numerals became cubes). Third, and general: after applying a fix, re-run the SAME measurement over ALL subjects and compare against the pre-change baseline -- the run that showed "changed nothing" and the run that showed "10 and 7 remaining" were both caught this way, and either could have shipped as a confident fix. Guard only the class you diagnosed: this filter is gated on `isChamfer` so a missing facet or glyph, where absence would be a visible hole, can never be silently dropped. Related: [[L-051]] (a metric merely NEAR the property certifies broken builds -- this is the same failure one level up, where the metric was pointed at the wrong PARTS), [[L-045]] (geometry is cheap to measure), [[L-031]]. -- Last Verified: 2026-08-15

### L-057: A nil in the Middle of an `ipairs` Fan-Out Silently Cancels Everything After It
- **Encountered State:** Dice Forge, 2026-08-16. The operator reported the settings panel "completely unhooked". It was far broader: EVERY menu panel was stale -- the slots headline was empty, none of fourteen shop cards showed its OWNED chip, and all four settings toggles read ACTIVE including the two gated on audio that does not exist. `V7MenuPanel.applyState` fans a snapshot out to seven refresher functions with `for _, fn in ipairs({ self.shopRefresh, self.shapeRefresh, ... })`. `refreshShop` had been re-declared with `local function` inside a nested block that closed several hundred lines before the controller table was built, so `shopRefresh = refreshShop` read an undeclared name and stored `nil` -- and `ipairs` STOPS AT THE FIRST nil. Shop was first in the list. Six unrelated panels went dark because of one scoping mistake in a seventh.
- **Root Cause Breakdown:** Two independently silent failures compounded. Lua does not warn when a name resolves to nothing, so `shopRefresh = refreshShop` is a legal read of an out-of-scope local and stores nil without complaint; and `ipairs` treats the first nil as the END of the array rather than as a gap, so the loop reported no error either. The blast radius is what makes this worth an entry: nothing in the failure pointed at the shop, and the panel the operator noticed -- settings -- was merely the one they happened to open. Diagnosis cost several rounds precisely because the symptom and the cause shared no file, no function and no obvious relationship. - **Definitive Fix Action:** Never fan out over an array literal that can contain a nil. Iterate a NAMED list -- `{ name = "shop", fn = self.shopRefresh }` -- skip a missing entry rather than terminating, and WARN which one is missing, so the next lost handler announces itself instead of the UI quietly going dead. Second: a display-layer calculation must never be able to cost the snapshot that feeds everything else; wrap it and degrade to "unknown" rather than letting it escape the handler. Third, and general: when a symptom spans many unrelated features, look for a SHARED chokepoint that runs before all of them rather than debugging the feature that was reported -- the operator names the panel they opened, not the panel that broke. ### L-058: `TextFits` Reports Truncation, Not Containment -- The Label Grew PAST Its Box

The screenshot showed the tier small print rendered straight THROUGH the buy buttons beneath it. More generally: when a fix changes an element sizing MODE, re-derive the acceptance check from the requirement instead of re-running the one that passed before, because a mode change can silently invalidate what the old check was measuring.
