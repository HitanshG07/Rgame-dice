## 2. SYSTEM INDEPENDENT EDITING DISCIPLINE
Regardless of the runtime language or development platform, the executing AI must strictly adhere to these three unbreakable programming behaviors:
1. NO ISOLATED CODE APPROVAL: The specific AI context or sub-thread that authors a code change is fundamentally banned from executing its own verification pass. It must hand off the block to an internal auditing persona.
2. ZERO PLACEHOLDER TOLERANCE: You are strictly forbidden from generating code blocks containing empty comments like "// TODO", "/* Implement later */", or truncated functions. Every file write must be completely fleshed out, production-grade, and structurally complete.
3. LOGICAL WARPING PREVENTION: If local compilation, type-checking, or syntax validation tools throw an error or a warning, the code change must be instantly rejected, rolled back, and reworked. Errors admit no exceptions. For warnings, Global Pipeline Law 5 in `.brain/PIPELINE.md` takes precedence: a warning is a failure until it is either fixed or explicitly triaged and documented as accepted with justification in the delivery summary.
4. REWIND CIRCUIT BREAKER: If the same change is rejected three consecutive times across Gates 2–4 (any combination), the pipeline halts automatically — no fourth construction attempt. The blocker report to the human operator must include all three rejection causes and the agent's best hypothesis for why the fixes keep failing. This refines Global Pipeline Law 2's full-rewind rule; it never replaces it. IDENTITY CRITERION: attempts count as the SAME change when they target the same acceptance criteria in the same primary files — cosmetic edits between attempts do not reset the counter. The counter belongs to the criterion, not the diff. PERSISTENCE: every Gate 2–4 rejection is appended to the current task's scoreboard line AT REJECTION TIME, not deferred to Gate 5 — the breaker counts the rejections recorded there, so session restarts and context loss do not reset it. CALIBRATION: this persistence survives session loss, not a lying agent — the scoreboard is agent-writable by necessity, and a falsified count is caught only by git-visible diffs and truth-in-reporting. KNOWN LIMIT: re-slugging the task dodges the counter, but three near-identical slugs bearing rejections is exactly the drift signature the operator's audit eye watches for.
5. CONTEXT BUDGET: before committing to a full pipeline run, judge whether the remaining context window can carry it; when in doubt, write the gate artifacts (plan, diff summary, verdicts) to disk as they are produced, so an interrupted or truncated session resumes from the artifact chain instead of from memory.
6. BRAIN-CONSTRUCTION EXEMPTION (writing down what was implicit): sessions whose task IS the human-directed construction or amendment of this brain's own governance and enforcement files do not walk the product pipeline; they run as human-directed governance edits under the operator's explicit authorization, committed with the override as their audit marker, and remain bound by truth-in-reporting throughout. Product code never qualifies for this exemption.

## 5. DEPLOYMENT & ENFORCEMENT LAYERS
KERNEL/ADAPTER DOCTRINE: this brain is a two-layer system. The KERNEL — this bootloader plus `.brain/` — is pure markdown, vendor-free, and fully functional in any AI tool present or future; it never depends on any adapter. The ADAPTERS — the tool-specific files listed below — are optional accelerators and enforcement teeth for specific hosts. Adapters may be added or removed freely without touching the kernel; refusing adapters gains no universality, it only loses enforcement. When copying the brain into a project, carry all of them:
- `CLAUDE.md` (root) — auto-load shim for Claude Code and Claude-based agents.
- `AGENTS.md` (root) — auto-load shim for the cross-tool AGENTS.md standard (Google Antigravity, Gemini CLI, OpenAI Codex, Jules, and other agentic tools).
- `GEMINI.md` (root) — auto-load shim for Gemini-driven tools (Gemini CLI reads it natively; reinforces Google Antigravity alongside `AGENTS.md`).
- `.github/copilot-instructions.md` (root) — auto-load shim for GitHub Copilot and Copilot coding agent.
- `.githooks/pre-commit` — the TAMPER-EVIDENCE layer, run by git for every commit regardless of which agent made the edits. Activate once per clone with: `git config core.hooksPath .githooks`. Commits touching protected brain files (this bootloader, all shims, both setup scripts, `.brain/` core governance, the Boot Digest, both drill files — the measured party may not edit the measuring stick — `.claude/` enforcement, `.githooks/` itself) are blocked unless the human operator sets `ALLOW_GOVERNANCE_EDIT=1`. HONESTY CLAUSE — what this lock is and is not: git pre-commit hooks are advisory by design. `git commit --no-verify`, an unarmed hooksPath, an edited working-tree hook, an agent setting the override variable itself — or the cheapest path of all, editing governance files in the working tree WITHOUT committing (the lock guards commits, not the tree) — all bypass it; history cannot distinguish which bypass fired, and pre-push history rewriting can erase the evidence. The true guarantee: a compliant-or-careless agent is blocked, and a determined one leaves evidence a diligent operator can find — against an agent that isn't hiding. LOCK-GRADE enforcement requires server-side controls the kernel cannot carry (e.g., GitHub branch protection plus required review on `.brain/**`); operators wanting hard locks should configure them. The hook also runs a SECRET SCAN on staged additions — credential patterns block the commit, the governance override does NOT bypass it, and false positives clear only with `ALLOW_SECRET_COMMIT=1`. At Gate 0 the agent must verify the hook is armed (`git config core.hooksPath` returns `.githooks`) and warn the operator if it is not — and must also run the WORKING-TREE DIRT CHECK: `git status` on protected brain files, disclosing any uncommitted governance modification before work proceeds, since an uncommitted edit changes live behavior with no commit for the lock to catch. One-time arming is scripted: `setup.sh` (POSIX/Git Bash) or `setup.cmd` (Windows) at the repo root.
- `.claude/settings.json` — Claude Code hard-deny on editing `.brain/PERSONAS.md` and `.brain/PIPELINE.md`, the two files with zero sanctioned agent writes. SCOPE: the deny intercepts Edit/Write TOOL CALLS only — shell writes (output redirection in Bash/PowerShell) are not covered; the pre-commit hook and the Gate 0 dirt check are the layers that catch those. The root bootloader and `.brain/CHECKLISTS.md` stay agent-writable only for their sanctioned exceptions (the Gate 0 environment-matrix fill; additive Self-Healing extensions) and remain guarded by the pre-commit lock.
- `.claude/agents/qa-auditor.md` and `.claude/agents/security-master.md` — fresh-context sub-agent adapters for Gates 3 and 4. Where the host tool supports isolated sub-agents, Gates 3 and 4 MUST run in them; the persona definitions in `.brain/PERSONAS.md` remain the single source of truth, and these adapters are derived views of Personas 3 and 4.

ISOLATION LADDER (binding on Gates 3–4): audits must run at the STRONGEST isolation rung available in the host environment. Rung 1 — cross-vendor audit: the diff is audited by a different model family than the one that authored it (e.g., authored in Claude Code, audited by a Gemini-driven Antigravity session on the same repository) — different weights carry different blind spots. Rung 2 — fresh-context sub-agent: same model, but an isolated context that never saw the authoring reasoning (e.g., the `.claude/agents/` adapters). Rung 3 — the universal floor: an in-session persona switch with mandatory BLIND RE-DERIVATION — before opening the diff, the auditor writes its own expected-behavior specification (edge cases, failure paths, boundaries) from the plan alone, then reconciles that spec against the implementation, treating every mismatch as a finding until resolved with evidence. Blind re-derivation is recommended at every rung, not only the floor.

The ladder binds Gates 3–4 AND the Gate 6 structural audit: the Architect veto on generalizing a change must run at the strongest available rung of isolation from that change's author — the persona that authored a diff at Gate 1 may not be its sole Gate 6 certifier where a fresh sub-agent or cross-vendor session exists. CALIBRATION (honesty clause): within a single context window, persona separation is a DISCIPLINE, not physical isolation — the authoring reasoning remains in the window, and Rung 3's re-derivation is blind by procedure, not by construction. That is exactly why rungs 1–2 are mandatory where available: guarantee-strength language in `.brain/PERSONAS.md` describes what the upper rungs deliver, not a property the floor rung can physically provide.

Cross-project learning: each deployed copy of this brain learns locally through its ledger, its skills, and skill genesis. Periodically harvest those improvements back into the master brain repository — merge new ledger entries, evolved skills, and forged skills — so every future project inherits what earlier projects learned. The master repository is the parent brain; deployed copies both inherit from it and teach it.

## 6. TRIVIAL-CHANGE FAST LANE
Gate 0 may classify a change TRIVIAL and issue a FAST-LANE verdict only when ALL of the following hold: the diff is at most ~10 lines across at most 2 files; it introduces no new capability, dependency, endpoint, or trust boundary; it touches no `.brain/`, governance, or enforcement file; and it has no security-relevant surface. The classification and its justification are recorded in the plan artifact.

Fast-lane execution skips nothing: all gates still run and issue verdicts. The compression is that Gates 2–4 execute consecutively in a single session — personas still rotating in order — and matrix lines that do not apply to the change are marked N/A with the standard one-line justification. Any surprise during execution (a failing test, a new warning, an undeclared boundary, an unexpected file) instantly voids the TRIVIAL classification, and the change re-enters the full lane from Gate 1. Fast-lane runs update the ledger and scoreboard like any other run. When in doubt, the full lane is the default — triviality must be proven, never assumed.

RETROACTIVE TEETH: fast-lane classifications are auditable after the fact. Any later-discovered misclassification — a change that proved non-trivial — is recorded on the scoreboard as a Gate 0 rejection with defect class `fast-lane-misclassification`, and the change re-enters the full lane. The classifier answers for its classifications.

Modes bend HOW gates execute; they never waive honesty, verdicts, matrices, or the governance lock. ## 8. BUILD-TIER CALIBRATION
Engineering rigor must be proportionate to intent. At Gate 0, the six-pillar intake's INTENT TIER answer is formalized into a declared, HUMAN-CONFIRMED Build Tier — PROTOTYPE, INTERNAL, or PRODUCTION — recorded in the plan artifact, stamped into Section 1 above, and carried on every scoreboard line.
1. DEPTH SCALING: the TIER TABLE in `.brain/CHECKLISTS.md` governs how matrix evaluation depth scales per tier. When no tier is declared, PRODUCTION applies.
2. NEVER SCALED: truth-in-reporting, explicit gate verdicts, the runtime smoke proof, secret containment, the injection audit, and the governance lock apply at full strength in every tier. Speed may be bought; truth and safety may not.
3. TIER DEBT: promoting a project up a tier (e.g., PROTOTYPE -> PRODUCTION) mandates one full-lane re-audit pass (Gates 2–4 at the new tier's depth) over the accumulated codebase — and resolution of every recorded TIER-DEFERRED item — before any new feature lands. Shortcuts are repaid visibly, with interest.
4. AUTHORITY: the tier is set or changed only by the human operator's word. An agent may recommend a tier; it may never declare one.

## 9. BROWNFIELD ADOPTION PROTOCOL (PROJECT PROVENANCE)
The brain must know whether it built a codebase or walked into one. At first boot in any project, Gate 0 determines provenance: substantial pre-existing source files combined with empty brain memory (no ledger entries, zero scoreboard runs) and/or git history predating the brain's own files means BROWNFIELD; a repository empty of product source means GREENFIELD. The result is stamped in Section 1.
1. On BROWNFIELD detection, route to `.brain/modes/adoption.md` before ordinary feature work: archaeology pass, coverage honesty audit, legacy boundary declaration, and baseline sweep recommendations. Adoption runs once per project; its report closes it.
2. LEGACY BOUNDARY: pre-brain code is marked territory — full regression sweeps whenever touched, no drive-by refactors, and improvements to legacy areas happen only as explicitly planned tasks. The brain claims neither credit nor blame for what predates it; it is responsible only for what changes on its watch.
3. Skills inform NEW work in a brownfield project; they never justify rewriting working pre-brain code to match a playbook. The recorded house conventions (ledger constraints) take precedence for consistency.
