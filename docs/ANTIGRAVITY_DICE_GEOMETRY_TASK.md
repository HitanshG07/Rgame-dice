## The bug

The five dice (D4, D6, D8, D12, D20) generated by `DiceMeshBuilder.generateAllDice()`
**render as six-pointed stars, not as solids.**

Every numeric property is already correct, which is why this went unnoticed:

- numerals are contiguous `1..N` with no duplicates
- face normals are recovered and unit-length, no two faces share one
- each model has a `PrimaryPart` at its centroid
- parts are positioned at the right distance from centre
- part counts are plausible (D6 = 19, D12 = 133, D20 = 61)

**Only the visual is wrong.** A D6 viewed from a corner angle looks like a
spiked star: each face's two triangles stick out PERPENDICULAR to the face they
belong to, instead of lying flat IN that face. So every face becomes a spike
radiating from the centre.

### Root cause, already localised for you

The defect is in **`draw3DTriangle`** (around line 45–150). It builds each
triangle from two `WedgePart`s. The *positions* it computes are right; the
*orientations* are wrong.

Specifically: the function computes `dirAC` (along the triangle's longest edge)
and `dirHeight` (perpendicular to it, toward the third vertex), then builds each
wedge's `CFrame` from those. The resulting wedge basis does not lie in the plane
of the triangle `(pA, pB, pC)` — it is rotated out of it. A wedge whose slope
runs out of the triangle's plane produces exactly the spike seen on screen.

Confirmed by inspection of a generated D6:

```
w1  pos=( 0.00,-1.24, 0.00) size=(0.23,2.48,2.48) right=(-1.0, 0.0, 0.0) up=( 0.0, 0.0, 1.0)
w2  pos=( 0.00, 0.00, 1.24) size=(0.23,2.48,2.48) right=( 0.0,-1.0, 0.0) up=(-1.0, 0.0, 0.0)
w3  pos=( 0.00, 1.24, 0.00) size=(0.23,2.48,2.48) right=( 1.0, 0.0, 0.0) up=( 0.0, 0.0, 1.0)
```

The positions are correct cube-face centres at ±1.24. But for the face at
`y = -1.24`, the wedge's thin axis (`Size.X = 0.23`) must point along **Y** (the
face normal). Its `right` vector points along X and its `up` along Z, so the
0.23-thick axis is NOT aligned with the face normal. That is the bug.

## What "fixed" means — the acceptance test

You are done when **all four** of these hold:

1. **A D6 rendered from an off-axis camera looks like a CUBE** — six flat square
   faces, straight silhouette, no spikes. Same for the other four shapes: D4 a
   tetrahedron, D8 an octahedron, D12 a dodecahedron, D20 an icosahedron.
2. **`generateAllDice()` still returns exactly 5 models** named `D4 D6 D8 D12 D20`,
   each with a `PrimaryPart`, a `FaceCount` attribute matching its shape, and
   `FaceNormal1..N` attributes that are unit-length `Vector3`s.
3. **Every die normalises to the same visual size** — `TARGET_EXTENT`, currently
   6.0 studs corner-to-corner. A D4 and a D20 must look like the same-sized
   object.
4. **No `warn()` fires** from the face-normal recovery check in `buildInto`.

### You are explicitly allowed to rewrite `draw3DTriangle` entirely

Do not feel obliged to preserve the wedge-pair approach. **A far simpler
construction is available and is probably the right answer:**

Every one of these five shapes is a regular (or near-regular) polyhedron. Each
face can be a SINGLE thin `Part` slab, positioned at the face centre and oriented
with `CFrame.lookAt(faceCentre, faceCentre + faceNormal)` so the slab's thin axis
runs along the normal. That is:

- ~5–20 parts per die instead of 12–132
- no trigonometry that can be wrong
- flat faces by construction, so spikes are impossible
- cheaper to render

A square face needs one slab; a triangular or pentagonal face can be a slab with
the right proportions, or you may keep wedges for triangles if you prefer — but
only if they lie in the face plane.

**Keep these, they are correct and other code depends on them:**

- the module's public API: `generateAllDice()` and `buildInto(parent)`
- `TARGET_EXTENT`, `normaliseScale`, `trueExtent`, `anchorPivot`,
  `recordFaceNormals`, `CATALOG_SHAPES`
- the `FaceLabel_N` numeral parts and their placement (face normals are recovered
  from them — if you move them, normals move with them, so keep them at face
  centres and facing outward)
- the rule that only the five catalog shapes are generated

### Final numeric verification, after the visual passes

```lua
local rs = game:GetService("ReplicatedStorage")
local Builder = loadstring((rs.Shared.DiceMeshBuilder :: ModuleScript).Source)()
local folder = Instance.new("Folder")
Builder.buildInto(folder)
local out = {}
for _, name in ipairs({"D4","D6","D8","D12","D20"}) do
    local m = folder:FindFirstChild(name)
    if not m then table.insert(out, name .. " MISSING") continue end
    local centre = m:GetPivot().Position
    local radius, parts = 0, 0
    for _, d in ipairs(m:GetDescendants()) do
        if d:IsA("BasePart") and d.Name ~= "Pivot" then
            parts += 1
            radius = math.max(radius, (d.Position - centre).Magnitude + d.Size.Magnitude * 0.5)
        end
    end
    local fc = m:GetAttribute("FaceCount")
    local bad = 0
    for i = 1, (fc or 0) do
        local n = m:GetAttribute("FaceNormal" .. i)
        if typeof(n) ~= "Vector3" or math.abs(n.Magnitude - 1) > 1e-3 then bad += 1 end
    end
    table.insert(out, string.format("%-4s parts=%-4d diameter=%.2f primary=%s faces=%s badNormals=%d",
        name, parts, radius * 2, tostring(m.PrimaryPart ~= nil), tostring(fc), bad))
end
folder:Destroy()
return table.concat(out, "\n")
```

Expected: 5 rows, `primary=true`, `faces` matching the shape, `badNormals=0`,
and every `diameter` equal to `TARGET_EXTENT` (6.00).
